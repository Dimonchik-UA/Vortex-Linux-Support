# IPC Contract

OVLS uses file-based JSON IPC for communication between the external Linux Support component and the Vortex Extension. The protocol is defined in Stage 9 of the OVLS project roadmap.

## Transport

Messages are exchanged as JSON files in a shared IPC directory under the Vortex prefix. The external component and the Extension each read/write files in designated subdirectories:

- `requests/` — outgoing request files from external component
- `processing/` — in-progress request files
- `responses/` — response files from Extension
- `acks/` — acknowledgment files
- `dedup/` — deduplication records for request IDs
- `quarantine/` — invalid or unprocessable requests
- `processed/` — completed request files
- `client_state/` — client-side acknowledgment confirmation files
- `sessions/<sessionId>/` — session-scoped directories for multi-request sessions

## Request Flow

1. External component writes a request JSON file to `requests/<requestId>.json`
2. Extension claims the request by atomically moving it to `processing/<requestId>.json`
3. Extension processes the request and writes response to `responses/<requestId>.json`
4. Extension writes dedup record to `dedup/<requestId>.json`
5. Extension writes acknowledgment to `acks/<requestId>.json`
6. External component reads response and sends ACK confirmation to `client_state/<requestId>.ack_confirmed.json`
7. Extension cleans up `processing/` and `acks/` files after confirmation

## Supported Request Types

| Request | Description |
|---------|-------------|
| `ping` | Connection test; returns pong with timestamp |
| `getState` | Reads Vortex state within allowlist |

Other request types are not currently supported. New commands are not added without a concrete use case.

## Error Codes

| Code | Meaning |
|------|---------|
| `INVALID_JSON` | Request file contains invalid JSON |
| `MISSING_REQUEST_ID` | Request missing request ID |
| `MISSING_REQUEST_TYPE` | Request missing type field |
| `UNSUPPORTED_PROTOCOL_VERSION` | Protocol version not supported |
| `UNKNOWN_REQUEST_TYPE` | Request type not recognized |
| `UNSAFE_STATE_PATH` | Requested state path not in allowlist |
| `STATE_PATH_NOT_ALLOWED` | State path explicitly denied |
| `IPC_STORAGE_LIMIT` | Storage limit exceeded |
| `RESPONSE_MISSING` | Expected response not found |
| `UNKNOWN_OUTCOME` | Outcome not recognized |

## Idempotency

- `ping`: Not strictly idempotent (timestamp changes)
- `getState`: Not guaranteed strictly idempotent (state may change between requests)
- `handleAck`: Idempotent delete operation
- `writeDedup`: Conditional idempotency (depends on TOCTOU protection)
- `claimRequest`: Not idempotent based on O_EXCL alone (exclusive creation ≠ idempotency)

## Session Management

Session identification and lifecycle are active areas of investigation. The following facts are confirmed:

- `sessionId` is generated by the Extension at startup (UUID v4).
- On first Extension load, a new `sessionId` is created.
- On renderer re-initialization (e.g., renderer process crash and reload via `loadURL()`), a new `sessionId` is generated, which breaks session continuity.
- Session identity across renderer restarts is **not** preserved by generating a new `sessionId` per initialization; this approach was rejected.

Open questions:

- Whether `sessionId` can be preserved across renderer restart using main process PID + starttime read from `/proc` is **not confirmed**. This remains an open question (OQ-5).
- No runtime-verified solution exists for preserving session identity across renderer restart as of this document's writing.

## TOCTOU and Dedup

- `writeDedup` performs read-modify-write without mutex/CAS/flock. In a single-process Extension, event loop serialization provides ordering, but this is not a general guarantee for multi-process access.
- The TOCTOU (time-of-check-time-of-use) problem in `writeDedup` is **not resolved**. No atomic protection for dedup status transitions is implemented.
- Repeated `claim` can change status from `completed` to `processing`, overwriting existing `ackProcessed`/`ackConfirmed` fields.

## Directory fsync Limitations

Under tested Proton 11.0, directory `fsync()` is unavailable (`EPERM`). File `fsync()` works. OVLS implements controlled degradation:

- `EPERM`/`ENOTSUP`/`EINVAL` → mandatory warning + limited guarantee; IPC continues
- `EIO`/`EISDIR`/unknown errors → propagated
- File fsync errors are not suppressed

Full durability against power loss is **not** claimed. Directory fsync unavailability has been observed under tested Proton 11.0; behavior under other Proton versions or configurations is not confirmed.

## Limitations

- IPC is file-based; no HTTP server is exposed by Vortex main process
- Only `ping` and `getState` are currently implemented
- Operations with side effects (mod installation, deletion) are not exposed via IPC
- Idempotency is not guaranteed for all operations
- Directory fsync is not available under Proton 11.0 (`EPERM`); durability is degraded but IPC continues

## Open Questions

- IPC root discovery mechanism (hybrid: environment variable + registration fallback) is not yet confirmed under Proton
- Heartbeat mechanism for session liveness is proposed but not runtime-verified
- Wine path conversion between Extension (Windows paths) and client (Linux paths) is not confirmed
