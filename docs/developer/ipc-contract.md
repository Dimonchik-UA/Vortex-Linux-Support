# IPC Contract

OVLS uses file-based JSON IPC for communication between the external Linux Support component and the Vortex Extension.

## Transport

Messages are exchanged as JSON files in a shared IPC directory under the Vortex prefix. The external component and the Extension each read/write files in designated subdirectories:

- `sessions/<sessionId>/requests/` — outgoing request files from external component (session-scoped)
- `sessions/<sessionId>/processing/` — in-progress request files (session-scoped)
- `sessions/<sessionId>/responses/` — response files from Extension (session-scoped)
- `acks/` — acknowledgment files (global)
- `dedup/` — deduplication records for request IDs (global)
- `quarantine/` — invalid or unprocessable requests (global)
- `processed/` — completed request files (global)
- `client_state/` — client-side acknowledgment confirmation files (global)
- `sessions/<sessionId>/` — session-scoped directories for multi-request sessions

> **Note:** The session-scoped layout is the only supported layout. The legacy flat layout (`requests/`, `responses/` at IPC root) is not supported by the production Extension or client.

## Request Flow

1. External component writes a request JSON file to `sessions/<sessionId>/requests/<requestId>.json`
2. Extension claims the request by atomically moving it to `sessions/<sessionId>/processing/<requestId>.json`
3. Extension processes the request and writes response to `sessions/<sessionId>/responses/<requestId>.json`
4. Extension writes dedup record to `dedup/<requestId>.json`
5. External component reads response and sends ACK to `acks/<requestId>.ack.json` (written by external component)
6. Extension reads ACK, creates `acks/<requestId>.acked` marker, updates dedup record
7. External component writes ACK confirmation to `client_state/<requestId>.ack_confirmed.json`
8. Extension processes ACK confirmation and cleans up `processing/` and `acks/` files

## Supported Request Types

| Request | Description |
|---------|-------------|
| `ping` | Connection test; returns pong with timestamp |
| `getState` | Reads Vortex state within allowlist |

Other request types are not currently supported. New commands are not added without a concrete use case.

## Error Codes

| Code | Meaning |
|------|---------|
| `INVALID_JSON` | Request file contains invalid JSON |
| `INVALID_REQUEST_ID` | Request ID is not a safe single path component |
| `CHECKSUM_MISMATCH` | Request checksum verification failed |
| `CHECKSUM_ERROR` | Checksum verification raised an error |
| `INVALID_REQUEST` | Request is not a JSON object |
| `UNSUPPORTED_PROTOCOL_VERSION` | Protocol version not supported |
| `MISSING_REQUEST_ID` | Request missing request ID |
| `MISSING_REQUEST_TYPE` | Request missing type field |
| `UNSAFE_STATE_PATH` | Requested state path not in allowlist |
| `UNKNOWN_REQUEST_TYPE` | Request type not recognized |
| `EXTENSION_ERROR` | Error raised while handling a valid request |
| `DUPLICATE_REQUEST` | Request ID has already completed and its result is not cached |

## Idempotency

- `ping`: Not strictly idempotent (timestamp changes)
- `getState`: Not guaranteed strictly idempotent (state may change between requests)
- `handleAck`: Idempotent delete operation
- `writeDedup`: Conditional idempotency (depends on TOCTOU protection)
- `claimRequest`: Not idempotent based on O_EXCL alone (exclusive creation ≠ idempotency); regression from `completed` to `processing` is prevented by dedup status check before claim

## Session Management

Session identification and lifecycle are active areas of investigation. The following facts are confirmed:

- `sessionId` is generated by the Extension at startup (UUID v4).
- On first Extension load, a new `sessionId` is created.
- On renderer re-initialization (e.g., renderer process crash and reload via `loadURL()`), a new `sessionId` is generated, which breaks session continuity.
- Session identity across renderer restarts is **not** preserved by generating a new `sessionId` per initialization; this approach was rejected.

Open questions:

- Whether `sessionId` can be preserved across renderer restart using main process PID + starttime read from `/proc` is **not confirmed**. This remains an open question (OQ-5).
- No runtime-verified solution exists for preserving session identity across renderer restart as of this document's writing.

## TOCTOU and Dedup

- `writeDedup` delegates to `mergeDedup`, which creates a per-request advisory lock `dedup/.lock-<requestId>` with `O_EXCL` (`wx`) and retries on `EEXIST` before giving up.
- A `completed` dedup record is never overwritten with `processing` (regression guard inside `mergeDedup`). The lock is a file lock, not a cross-process CAS guarantee; stale `.lock-` files are not cleaned automatically.
- Repeated `claim` cannot change status from `completed` to `processing` because the Extension checks dedup status before claiming (see Request Flow step 2 guard in `pollOnce`).

## Directory fsync Limitations

Under tested Proton 11.0, directory `fsync()` is unavailable (`EPERM`). File `fsync()` works. OVLS implements controlled degradation:

- `EPERM`/`ENOTSUP`/`EINVAL` → mandatory warning + limited guarantee; IPC continues
- `EIO`/`EISDIR`/unknown errors → propagated
- File fsync errors are not suppressed

Full durability against power loss is **not** claimed. Directory fsync unavailability has been observed under tested Proton 11.0; behavior under other Proton versions or configurations is not confirmed.

## Limitations

- IPC is file-based; no HTTP server is exposed by Vortex main process
- Only `ping` and `getState` are currently implemented
- Operations with side effects (mod installation, deletion) are not exposed via IPC
- Idempotency is not guaranteed for all operations
- Directory fsync is not available under Proton 11.0 (`EPERM`); durability is degraded but IPC continues

## Open Questions

- The Extension always uses the fixed `<userData>/OVLS_IPC_V2` directory; there is no discovery mechanism. The CLI requires `--ipc-dir`, the Python client uses `$OVLS_IPC_DIR` or `~/.ovls_ipc_v2`, and stale-file cleanup uses a hardcoded prefix path.
- Heartbeat mechanism for session liveness is proposed but not runtime-verified
- Wine path conversion between Extension (Windows paths) and client (Linux paths) is not confirmed
